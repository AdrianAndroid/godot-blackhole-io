# Design

## Context

当前项目是绿色工程：已有参考视频、OpenSpec 配置、6 套候选素材及授权清单，但没有 `project.godot`、场景、脚本或测试。首关选用 Commercial、Roads、Suburban、Industrial 中适合的 GLB 资源；Tiny Town 不用于主视觉，UI Pack 仅作组件参考。

用户已确认 Mac 原型优先、实时 3D 模型、XZ 平面逻辑、Mobile 渲染器、完整单局闭环和全自动化验收。抖音适配、固定帧率门槛和完整 AI 均不在本轮约束内。需求契约见 `proposal.md` 与 `specs/`。

## Goals / Non-Goals

**Goals:**

- 将确定性玩法状态与实时 3D 表现分离，使同一规则可在 headless 和图形测试中复现。
- 用显式数据配置建筑、成长、目标、对手路线和镜头，避免数值散落。
- 让随机地图、一次性吞噬结算、对局结束和重开均具备确定性测试接口。
- 保留参考视频的竖屏构图、成长反馈、竞争威胁和最终高塔闭环。
- 原始素材不可变，正式导入资源、字体和音效均可追溯。

**Non-Goals:**

- 不使用完整刚体物理、实时建筑破坏、跳跃或垂直移动。
- 不实现完整 AI、真人联机、抖音 SDK、跨局存档或永久养成。
- 不在本轮预先承诺固定帧率、所有素材模型全部使用或主观音效等同于视频。
- 不把自动截图比较表述为人类审美验收，也不以 headless 测试替代真实图形渲染检查。

## Decisions

### 1. 实时 3D 场景承载 XZ 平面玩法

对局根节点使用 `Node3D`，地面设为 XZ 平面，Y 仅用于模型高度和吞噬下沉。玩家与假对手使用 `Node3D` 移动主体和 `Area3D` 做候选目标宽阶段检测，最终资格在逻辑层用 XZ 距离、占地半径和有效洞口半径判断。

大型不可吞建筑不设置会排斥玩家的实体碰撞体。玩家移动由 `_physics_process(delta)` 中的受控平面位移完成，不依赖 `RigidBody3D`。这样可以直接呈现 GLB，同时保留稳定的街机式穿透和吞噬规则。

**备选方案：**预渲染 2D 精灵被用户明确否决；完整 3D 物理会增加穿透、抖动、性能和自动测试的不确定性；独立 2D 坐标映射会增加同步成本。

### 2. 单一 Session 根节点与明确管理职责

每场对局拥有独立的 Session 根节点，首页与结算不持有上一场玩法对象。核心职责如下：

- `GameManager`：状态机、固定事件顺序、倒计时、暂停、唯一结果和重试。
- `CityGenerator`：模板、种子、区域、布局签名、出生点和合法性校验。
- `SpawnManager`：按布局描述实例化模型、玩家、假对手和高塔。
- `GrowthManager`：19 级经验、阈值、有效半径与升级事件。
- `SwallowManager`：吞噬声明、进度、取消与一次性完成事件。
- `ObjectiveManager`：目标分、完成度、金币、击倒奖励和高塔状态。
- `InputController`：触摸/鼠标统一输入及取消语义。
- `FollowCamera`：跟随、成长缩放、边界和投影切换。
- `HudController`、`AudioManager`：订阅事件，不拥有玩法事实。

配置采用自定义 `Resource` 或只读数据文件，运行状态不写入共享素材资源。除应用级场景切换外，优先通过 Session 组合根显式连接依赖，减少自动加载单例造成的重开残留。

### 3. 可复现地图使用局部随机流

生成管线固定为：道路模板 → 街区与用途分区 → 地块建筑 → 小型物体与装饰 → 出生点和对手路线 → 高塔预留 → 合法性校验。所有随机选择来自本局局部种子随机流，不混用全局 `randf()`、时间或节点遍历顺序。

每个实例包含稳定 ID、模型 ID、变换、区域、地面占地半径、经验、目标分、金币和体型层级。布局签名由排序后的稳定字段计算，用于相同种子比较和新局换图检查。

生成失败时使用由“原种子＋尝试序号”确定的子随机流重建，保证同一原种子即使经过重试仍得到同一最终布局。种子、生成版本和尝试序号写入测试报告。

**备选方案：**全图自由随机摆放难以保持道路连通、成长路径和城市观感；纯固定地图不符合用户选择。

### 4. 模型注册表统一视觉尺度与玩法尺度

为每个正式选用的 GLB 建立模型注册项，至少记录：

- 资源路径、来源包、变体和授权记录链接。
- 统一缩放、地面原点修正、默认朝向。
- 地面占地半径与吞噬视觉中心。
- 区域标签、体型层级、经验、目标分和金币。

占地半径以模型在地面上的实际包围范围为基础，经导入校验场景修正，不使用整栋建筑高度作为半径。黑洞有效半径与 Shader 圆盘共享同一配置值，避免“看起来能吞但判定不能吞”。

原始 `source.zip` 和 `extracted/` 不修改。正式选用资源复制到独立游戏资源目录，候选目录继续由 `.gdignore` 排除。

### 5. 吞噬采用声明与完成两阶段事务

普通物体状态为 `IDLE → CLAIMED → SINKING → SETTLED`。满足半径条件后由 `SwallowManager` 声明唯一归属，其他黑洞不能重复获取。逻辑层按固定时长推进吞噬，表现层据此更新倾斜、缩小、位置和下沉；完成时先标记 `SETTLED`，再原子化发出奖励事件并移除对象。

奖励只由完成事件产生，动画回调、碰撞重复信号和节点退出均不得直接加分。对局结束或 Session 销毁会取消未完成的声明，不补发奖励。最终高塔复用同一事务，但通过明确的目标类型绕过普通半径资格，且只发放胜利而不发普通建筑奖励。

**备选方案：**在 Tween 回调里直接加分实现较快，但暂停、重开、重复信号和测试加速时容易重复结算。

### 6. 数值系统分离并集中配置

`GrowthManager` 只处理经验和 1～19 级半径；`ObjectiveManager` 只处理目标分、完成度、本局金币和击倒奖励。首关目标分采用 `ceil(全部普通建筑目标分 × 0.75)`，使建筑本身必然提供足够预算，击倒奖励只提供额外余量。

19 级经验阈值和有效半径由单调数值表配置。初版通过自动模拟调整升级节奏，不在运行中根据玩家表现动态改表。满级后经验可记录但不再改变半径。

假对手互吞采用可配置的优势倍率，初值设为 `1.10`：较大方有效半径必须大于较小方的 110%。该值是“明显更大”的实现默认，不是从视频反推的事实。本轮仅处理玩家与假对手之间的互吞；假对手彼此不互吞，避免固定路线造成不可控减员。

### 7. 假对手使用确定性路线，不引入导航系统

地图生成器为 4 个假对手生成闭合路线、初始半径、颜色和出生点。对手按固定速度沿 XZ 节点插值移动，不运行寻食、追击、逃跑或 `NavigationAgent3D`。路线通过出生安全校验，较大对手不得覆盖玩家初始位置。

这种实现足以验证镜头遮挡、体型威胁、互吞、死亡、击倒和多重击倒，不会提前扩大为完整 AI 项目。

### 8. 固定状态顺序保证唯一结局

状态包括 `HOME`、`READY`、`PLAYING`、`PAUSED` 和 `RESULT`。倒计时使用游戏更新时间，不读取系统墙钟。Esc 显式切换暂停；窗口失焦通知不改变状态。

每个逻辑周期按固定顺序处理：输入与移动 → 吞噬完成 → 玩家死亡 → 高塔胜利 → 超时。首个不可逆结果锁定 Session，后续事件忽略。默认同周期优先级为玩家死亡、高塔胜利、超时；测试覆盖边界条件。

重试通过销毁整个 Session 并创建新实例完成，沿用种子与生成版本；从首页开始则请求不同布局签名的新种子。输入、音频、Tween、计时器和临时 UI 均属于 Session 或具有明确释放入口。

### 9. 输入与镜头共用统一抽象

`InputController` 输出标准化二维向量，并维护唯一活动触摸 ID。鼠标左键模拟同一浮动摇杆，释放、取消和 Session 销毁均清零。第二根手指不改变输入所有权。

镜头使用同一 `Camera3D` 切换 `PROJECTION_PERSPECTIVE` 与 `PROJECTION_ORTHOGONAL`，默认透视。跟随位置、成长缩放和地图约束只改变观察，不写回玩法坐标。设计视口采用与参考视频一致的 9:20 竖屏比例，基准为 432×960；窗口缩放只改变显示，不改变移动速度或判定。

### 10. 画面优先采用 Mobile 渲染器的可控 3D 配置

工程使用 Godot 4.7.2、GDScript 和 Mobile 渲染后端。城市直接使用导入 GLB，采用统一环境光、方向光、材质和尺度；Commercial 彩色变体按街区混合，Suburban 与 Industrial 作为不同区域。先实现接近参考的画面，再通过自动性能报告决定优化，不预设 60/30 FPS 通过线。

黑洞使用水平 3D 圆盘网格和 Spatial Shader，表现深色中心、旋转纹理、彩色外圈与吸附动画。物体下沉利用地面遮挡与模型变换完成，不构造真实凹陷地形。建筑遮挡玩家的可读性通过固定种子截图检查，必要时调整材质遮挡淡化，而不是新增实体碰撞。

HUD 采用 `CanvasLayer` 和中文开源字体。思源黑体或 Noto Sans SC 在具体下载时根据授权文件和体积二选一，记录许可证。音效只接入明确授权的音频文件，事件订阅保证一次完成只播放一次。

### 11. 自动验收分为逻辑、整局、图形和性能四组

不引入未经用户确认的第三方测试插件，先建立项目内 GDScript 测试入口和统一命令：

- **逻辑测试**：headless 运行纯数据、成长、目标、吞噬事务、状态机、输入状态和种子校验。
- **整局测试**：通过输入抽象和自动驱动器运行，使用固定步进加速，覆盖胜利、被吞、超时、暂停和重试；不允许测试直接改写结果来冒充流程通过。
- **图形测试**：以非 headless Godot 自动启动固定种子与镜头，注入输入、到达检查点并读取 `Viewport` 截图。固定渲染器、分辨率、种子和时间点，输出基线差异图；基线只能显式更新。
- **性能测试**：真实图形环境定时采样帧时间、对象数、渲染统计和可用内存，保存 JSON/Markdown 报告，不设本轮固定 FPS 门槛。

统一入口汇总退出码、失败日志、种子、截图和性能结果。音频自动验证事件次数和播放状态，不声称完成主观听感验收。所有测试由开发方执行，不要求用户手工参与。

### 12. 本地 Git 与资产边界

实现开始时初始化本地 Git，不创建或推送远程仓库。忽略 `.godot/`、系统文件、自动测试输出和 `assets/candidates/*/extracted/`；原始 ZIP、许可证、清单和预览入库。正式模型、字体、音效及其授权单独入库。

阶段提交只包含当前阶段已验证文件，原始视频与候选解压目录保持本地可用。回滚通过 Git 阶段提交完成，不覆盖或重新解压原始包来“修复”正式资源。

## Risks / Trade-offs

- **实时 3D 在竖屏密集城市中可能产生较大性能开销** → 先按画质目标实现并保留采样报告；后续再按实际瓶颈调整阴影、可见范围、实例化和材质，不提前承诺帧率。
- **GLB 的枢轴、单位和纹理变体可能不统一** → 建立模型注册表与导入校验场景，逐类记录修正，不修改原始文件。
- **随机地图可能缺少初期目标或无法达到完成度** → 生成后自动校验、确定性重试、记录种子，并批量执行种子测试。
- **黑洞穿到高楼下方时可能被完全遮挡** → 以截图场景验证可读性，必要时使用局部遮挡淡化或轮廓提示，不改变穿透规则。
- **逻辑时长大于动画或重复信号可能造成奖励竞态** → 逻辑事务拥有唯一完成权，视觉只订阅进度，结果锁定后取消未完成事务。
- **headless 无法验证真实 Shader、字体和画面** → 自动增加非 headless 图形测试，明确区分逻辑通过与视觉通过。
- **自动整局驱动可能只覆盖理想路径** → 同时加入负向路径、不变量和批量种子，不允许直接设置胜负状态替代完整流程。
- **Mac 优先不能证明未来抖音兼容** → 将渲染、输入和资源加载边界保持独立，抖音链路另立技术验证变更。
- **画质优先且没有固定性能门槛** → 本轮只能声明已采样和满足功能验收，不能声明已完成性能优化。

## Migration Plan

1. 初始化本地 Git 和 Godot Mobile 工程，提交忽略规则与工程基线。
2. 建立 GLB 导入校验、统一镜头和黑洞 Shader 的最小视觉场景，自动生成两种投影截图。
3. 实现确定性数据配置、地图生成、移动、吞噬、成长和目标，先通过 headless 测试。
4. 接入假对手、完整对局状态、HUD、音效和结算，再通过自动整局测试。
5. 执行批量种子、视觉基线和性能采样，修复后形成最终阶段提交。

这是对最初节点约定的设计替换，但当前尚无旧游戏代码或存档，因此不需要数据迁移。任何阶段回退都只恢复 Git 中的正式工程与资源，候选原包保持不变。

## Open Questions

- 19 级的具体经验阈值、半径曲线和各类物体分值，可在自动平衡测试中调整，只要不改变已确认规则。
- 每个城区最终选用的具体模型、光照参数和 Commercial 变体比例，可通过视觉基线迭代确定。
- 基础音效的具体 CC0 文件和中文字体最终选择，需以实际下载包的授权与体积确定。
- 后续性能优化项目和抖音导出方案由实际报告决定，不影响本轮任务边界。
